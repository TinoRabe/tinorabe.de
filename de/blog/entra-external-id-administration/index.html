Entra External ID für Power Pages: Administrator-Handbuch

    1. Einleitung und Zielsetzung

    Zielsetzung

    Dieses Dokument beschreibt die administrativen Aufgaben bei der Verwaltung von Microsoft Entra External ID (einem externen Tenant) für die Integration mit Microsoft Power Pages. Es unterscheidet klar zwischen einmaligen Setup-Aufgaben und laufenden Wartungsarbeiten.

    External ID ist nicht Azure AD B2C

    Microsoft Entra External ID ist die aktuelle CIAM-Lösung von Microsoft. Sie läuft in einem eigenen externen Tenant, den Sie im Microsoft Entra Admin Center verwalten. Azure AD B2C ist ein separates Altprodukt: Seit dem 1. Mai 2025 wird es nicht mehr an Neukunden verkauft, unterstützt wird es mindestens bis Mai 2030. B2C-Konzepte wie B2C_1_-Policies, Custom Policies (Identity Experience Framework) oder AADB2C-Fehlercodes gelten für External ID nicht.

    Zielgruppe

    IT-Administratoren und Identity-Verantwortliche mit Grundkenntnissen in Azure/Entra ID. Technisches Verständnis von OAuth2/OpenID Connect ist hilfreich, aber nicht zwingend erforderlich.

    2. Übersicht: Einmalige vs. Regelmäßige Aufgaben

    Einmalige Setup-Aufgaben

    Diese Aufgaben fallen einmalig bei der Ersteinrichtung an:

    • Externen Tenant erstellen
    • App-Registrierung konfigurieren
    • User Flow einrichten (Registrierung/Anmeldung)
    • Company Branding konfigurieren
    • MFA per Conditional Access erzwingen
    • Integration mit Power Pages
    • Testbenutzer anlegen und Tests durchführen

    Regelmäßige Wartungsaufgaben

    Diese Aufgaben fallen im laufenden Betrieb an:

    • Sign-in Logs überwachen
    • Fehlgeschlagene Anmeldungen prüfen
    • Inaktive Benutzer deaktivieren
    • Client Secrets rotieren (nur falls eines verwendet wird)
    • Änderungen am User Flow testen
    • Kapazität und Kosten überwachen
    • Sicherheitsupdates verfolgen

    Wichtig

    Nach erfolgreichem Setup ist der administrative Aufwand gering. Die meisten Tätigkeiten beschränken sich auf Monitoring und gelegentliche Anpassungen. Portal-Benutzer setzen ihr Passwort selbst zurück; Profildaten werden in Power Pages gepflegt.

    3. Einmalige Setup-Aufgaben

    3.1 Externen Tenant erstellen
    Einmalig

    Erstellen Sie einen dedizierten externen Tenant für die Portal-Authentifizierung. Externe Tenants werden im Microsoft Entra Admin Center angelegt, nicht im Azure Portal.

    Vorgehensweise:
    1. Im Microsoft Entra Admin Center navigieren zu: Entra ID > Overview > Manage tenants
    2. "Create" wählen, "External" auswählen und fortfahren
    3. 30-Tage-Trial oder "Use Azure Subscription" wählen
    4. Tenant-Name und Domain-Name eingeben (z.B. portalauth)
    5. Land/Region wählen (für die DSGVO: ein EU-Land)
    6. Abonnement und Ressourcengruppe wählen, dann erstellen (dauert bis zu 30 Minuten)
    Wichtige Einstellungen:
    • Domain: [name].onmicrosoft.com wird angelegt; die Anmeldung läuft über [name].ciamlogin.com
    • Rolle: Zum Anlegen ist mindestens die Rolle Tenant Creator nötig
    • Abrechnung: MAU-basiert über das verknüpfte Azure-Abonnement

    Wichtig:

    Land/Region (Datenstandort) und Domain-Name lassen sich nach der Erstellung nicht mehr ändern. Wählen Sie sorgfältig.

    3.2 App-Registrierung konfigurieren
    Einmalig

    Registrieren Sie im externen Tenant eine Anwendung für die OpenID-Connect-Anmeldung mit Power Pages.

    Zuerst die Reply URL aus Power Pages holen:
    1. Im Power Pages Design Studio: Security > Identity providers
    2. Bei "Microsoft Entra External ID" auf "Configure" klicken, Namen eingeben, "Next"
    3. Reply URL kopieren und den Tab offen lassen
    Vorgehensweise:
    1. Im externen Tenant navigieren zu: App registrations > New registration
    2. Namen vergeben: power-pages-app
    3. Redirect URI: Plattform "Web", die aus Power Pages kopierte Reply URL einfügen (bei eigener Domain: die entsprechende URL Ihrer Domain)
    4. Registrierung abschließen
    5. Authentication: Access tokens und ID tokens aktivieren, speichern
    6. API permissions: Grant admin consent wählen

    Client Secret:

    Laut Power-Pages-Dokumentation fragt der eigene Provider "Microsoft Entra External ID" nur Client ID, Authority, Redirect URL und Metadata address ab. Ein Client Secret brauchen Sie nur, wenn Sie External ID über den generischen OpenID-Connect-Provider mit Authorization Code Flow anbinden.

    Sicherheit:

    Falls Sie ein Client Secret verwenden: niemals in Code oder öffentlichen Repositories speichern. Bewahren Sie es in einem Tresor wie Azure Key Vault auf und notieren Sie das Ablaufdatum.

    3.3 User Flow einrichten
    Einmalig

    External ID kennt einen User-Flow-Typ für Registrierung und Anmeldung. Der Passwort-Reset ist Teil der Anmeldung, kein eigener Flow.

    Registrierungs- und Anmelde-Flow erstellen:
    1. Navigieren zu: Entra ID > External Identities > User flows > New user flow
    2. Namen vergeben: power-pages-user-flow (kein Präfix nötig)
    3. Identity providers, Email Accounts:
      • Email with password (Standard) oder Email one-time passcode
      • Optional: Google, Facebook, Apple oder Custom OIDC, sobald sie im Tenant als Identity Provider eingerichtet sind
    4. Benutzerattribute für die Registrierung auswählen, dann "Create"
    5. Im User Flow: Applications > Add application, power-pages-app auswählen
    Benutzerattribute festlegen:

    Legen Sie fest, welche Daten bei der Registrierung erfasst werden:

    Attribut Bei Registrierung erfassen Pflicht
    E-Mail-Adresse Ja (immer, per Einmalcode verifiziert) Ja
    Vorname (Given Name) Ja Empfohlen
    Nachname (Surname) Ja Empfohlen
    Anzeigename (Display Name) Optional Nein

    Attribute werden nur bei der ersten Registrierung abgefragt. Welche Werte in Power Pages ankommen, steuern die App-Registrierung (Token configuration) und das Claims Mapping in Power Pages.

    Passwort-Reset aktivieren:
    1. Voraussetzung: Der User Flow nutzt Email with password
    2. Navigieren zu: Entra ID > Authentication methods > Email OTP
    3. Email OTP für alle Benutzer (oder ausgewählte Gruppen) aktivieren und speichern
    4. Benutzer sehen dann auf der Anmeldeseite den Link "Forgot password?"

    Tipp:

    Testen Sie jeden User Flow direkt nach dem Anlegen mit "Run user flow" im Microsoft Entra Admin Center.

    3.4 Company Branding konfigurieren
    Einmalig

    Passen Sie die von Microsoft gehosteten Anmeldeseiten an Ihr Corporate Design an. Externe Tenants starten mit einem neutralen Branding ohne Microsoft-Logos.

    Branding-Optionen:
    1. Navigieren zu: Entra ID > Custom Branding, Reiter "Default sign-in" > "Edit"
    2. Basics: Favicon, Hintergrundbild, Hintergrundfarbe
    3. Layout: Template (Voll- oder Teilbild), Header, Footer
    4. Header und Anmeldeformular: Logo und Banner-Logo
    5. Footer: eigene Links zu Datenschutz und Nutzungsbedingungen
    6. Text: eigene Texte für Anmeldung und Registrierung
    7. Sprachen: über die Sprachanpassung im User Flow

    Custom CSS läuft aus:

    Microsoft stellt Custom CSS für das Company Branding schrittweise ein. Tenants, die nach dem 5. Januar 2026 angelegt wurden, bekommen es nicht mehr. Planen Sie Ihr Branding mit den eingebauten Optionen. Eigene HTML-Seiten (wie aus B2C bekannt) gibt es in External ID nicht.

    Barrierefreiheit:

    Achten Sie bei Hintergrundbildern und Farben auf ausreichende Kontraste und WCAG-Konformität.

    3.5 Multi-Faktor-Authentifizierung (MFA)
    Einmalig

    In externen Tenants wird MFA über eine Conditional-Access-Richtlinie erzwungen, nicht über eine Einstellung im User Flow.

    MFA aktivieren:
    1. Methoden für den zweiten Faktor unter Entra ID > Authentication methods aktivieren:
      • Email OTP: einfachste Methode (als zweiter Faktor nach E-Mail und Passwort)
      • SMS: als kostenpflichtiges Add-on verfügbar
      • Passkey (FIDO2): phishing-resistent
    2. Richtlinie anlegen unter Conditional Access > New policy:
      • Users: alle Benutzer, Notfallkonten ausschließen
      • Target resources: die Power-Pages-App (oder alle Ressourcen)
      • Grant: Multifaktor-Authentifizierung erforderlich
    3. Richtlinie aktivieren und mit einem Testbenutzer prüfen

    Empfehlung:

    Aktivieren Sie MFA mindestens für administrative Konten. Für normale Portal-Benutzer kann MFA optional bleiben, sollte aber geprüft werden.

    3.6 Integration mit Power Pages
    Einmalig

    Power Pages hat einen eigenen Identity Provider für External ID. Nutzen Sie ihn statt eines generischen OpenID-Connect-Providers.

    Benötigte Angaben aus der App-Registrierung:
    Client ID: Application (client) ID (Overview) Authority: Authority URL (Endpoints) Metadata address: OpenID Connect metadata document (Endpoints), Format: https://[tenant].ciamlogin.com/[tenant-id]/v2.0/.well-known/openid-configuration

    Kopieren Sie die Werte aus App registrations > [Ihre App] > Endpoints, statt sie von Hand zusammenzubauen. URLs im B2C-Stil mit Policy-Namen (B2C_1_...) oder b2clogin.com funktionieren mit External ID nicht.

    Konfiguration in Power Pages:
    1. Zurück zum offenen Tab (Design Studio: Security > Identity providers > Microsoft Entra External ID)
    2. Konfiguration eintragen:
      • Client ID, Authority und Metadata address: [siehe oben]
      • Redirect URL: Standardwert belassen; bei eigener Domain die eigene URL eintragen (muss exakt der Redirect URI der App-Registrierung entsprechen)
    3. Optionale Zusatzeinstellungen: External logout, Claims mapping, Nonce lifetime, Use token lifetime, Contact mapping with email
    4. "Confirm" wählen

    Tipp:

    Änderungen an der Authentifizierung können einige Minuten dauern. Für sofortige Wirkung die Website im Power Pages Admin Center neu starten.

    Tipp:

    Deaktivieren Sie nach erfolgreicher Integration andere Identity Provider (lokaler Login, Microsoft), wenn ausschließlich Entra External ID genutzt werden soll.

    3.7 Tests durchführen
    Einmalig

    Führen Sie umfassende Tests durch, bevor das System produktiv geht.

    Testszenarien:
    1. Registrierung: Neuen Benutzer anlegen und E-Mail-Verifizierung prüfen
    2. Anmeldung: Mit dem neuen Konto anmelden
    3. Passwort-Reset: "Forgot password?" komplett durchlaufen
    4. MFA: Multi-Faktor-Authentifizierung testen (falls aktiviert)
    5. Claims: Prüfen, ob alle benötigten Werte in Power Pages ankommen (Kontakt-Datensatz)
    6. Abmeldung: Sign-out testen (inkl. External logout, falls aktiviert)
    7. Fehlerfälle: Falsche Anmeldedaten, abgelaufene Sitzung usw. testen

    Go-Live-Checkliste:

    Das System sollte erst nach erfolgreichen Tests in allen Szenarien für produktive Benutzer freigegeben werden.

    4. Regelmäßige Wartungsaufgaben

    4.1 Sign-in Logs überwachen
    Täglich

    Überwachen Sie Anmeldeaktivitäten auf Auffälligkeiten und Fehler.

    Zugriff auf die Logs:
    1. Im Microsoft Entra Admin Center: Entra ID > Monitoring & health > Sign-in logs
    2. Filter setzen:
      • Zeitraum: letzte 24 Stunden
      • Status: Failure
      • Anwendung: power-pages-app
    3. Auffälligkeiten prüfen (z.B. viele Fehlversuche von derselben IP)
    Wichtige Kennzahlen:
    • Fehlgeschlagene Anmeldungen: sollten unter 5 % liegen
    • MAU (monatlich aktive Benutzer): für die Kostenkontrolle
    • Anmeldedauer: Performance-Indikator
    • MFA-Erfolgsquote: falls MFA aktiviert ist

    Alarmierung einrichten:

    Externe Tenants bewahren Sign-in- und Audit-Logs nur 7 Tage auf. Exportieren Sie sie per Azure Monitor in einen Log-Analytics-Workspace und richten Sie dort Alarme für ungewöhnlich hohe Fehlerraten ein.

    4.2 Inaktive Benutzer deaktivieren
    Monatlich

    Identifizieren und deaktivieren Sie Konten, die längere Zeit nicht genutzt wurden.

    Vorgehensweise:
    1. Benutzer ohne Anmeldung seit mehr als 90 Tagen ermitteln (aus den nach Log Analytics exportierten Sign-in Logs oder per Microsoft Graph)
    2. Im Microsoft Entra Admin Center: Entra ID > Users
    3. Liste exportieren und mit dem Fachbereich abstimmen
    4. Konten deaktivieren (nicht löschen!):
      • Benutzer auswählen
      • Eigenschaften > Account enabled: Nein
    5. Dokumentation aktualisieren

    Hinweis:

    Deaktivierte Konten lassen sich jederzeit reaktivieren. Endgültig gelöscht werden sollte nur nach ausdrücklicher Freigabe (z.B. DSGVO-Löschanfrage).

    4.3 Client Secrets rotieren
    Halbjährlich

    Nur relevant, wenn Ihre Konfiguration ein Client Secret nutzt (z.B. generischer OpenID-Connect-Provider mit Authorization Code Flow). Der eigene External-ID-Provider nutzt keines, wenn er nach der Microsoft-Dokumentation eingerichtet ist.

    Ablauf der Rotation:
    1. Neues Client Secret anlegen (Certificates & secrets > New client secret)
    2. Beide Secrets parallel aktiv lassen
    3. Power-Pages-Konfiguration auf das neue Secret umstellen
    4. Testen (Anmeldung, Registrierung)
    5. Altes Secret nach 48 Stunden löschen
    6. Vorgang dokumentieren

    Wichtig:

    Stimmen Sie die Rotation mit dem Power-Pages-Team ab. Ungeplante Secret-Wechsel führen zu Anmeldefehlern.

    4.4 Kapazität und Kosten überwachen
    Monatlich

    Überwachen Sie die monatlich aktiven Benutzer (MAU) und die zugehörigen Kosten.

    Kostenkontrolle:
    • Preismodell: Entra External ID wird nach MAU abgerechnet
    • Kostenlos: die ersten 50.000 MAU pro Monat
    • Darüber hinaus: Abrechnung pro MAU; Premium-Add-ons (z.B. SMS für MFA) haben kein Freikontingent. Aktuelle Preise: offizielle Preisseite von External ID
    1. Im Azure Portal: Cost Management > Cost analysis auf dem Abonnement bzw. der Ressourcengruppe, die mit dem Tenant verknüpft ist
    2. Die Nutzung erscheint dort auch, solange Sie unter dem Freikontingent liegen
    3. Trend-Analyse: MAU-Entwicklung der letzten 3 Monate
    4. Budget-Alarme einrichten (optional)
    4.5 Sicherheitsupdates und Änderungen
    Quartalsweise

    Prüfen Sie regelmäßig angekündigte Änderungen und Sicherheitshinweise.

    Quellen:
    1. Azure Portal: Service Health > Planned maintenance
    2. Microsoft 365 Message Center abonnieren
    3. "What's new" für Microsoft Entra External ID verfolgen
    4. Security Advisories prüfen

    Automatische Updates:

    Die meisten Updates spielt Microsoft automatisch ein. Manuelle Anpassungen sind nur bei Breaking Changes nötig, etwa beim Auslaufen von Custom CSS oder der User-Insights-Dashboards.

    5. Monitoring und Troubleshooting

    5.1 Dashboard-Kennzahlen

    Kennzahl Normalwert Alarmwert Maßnahme
    Fehlgeschlagene Anmeldungen < 5% > 10% Sign-in Logs prüfen, User Flow testen
    Anmeldedauer < 3s > 10s Performance-Analyse, Azure Support
    Token-Fehler < 1% > 5% Token-Konfiguration prüfen, Claims validieren
    MAU-Wachstum Gleichmäßig Plötzlicher Sprung Bot-Aktivität prüfen, Kosten-Alarm

    5.2 Häufige Fehler und Lösungen

    External ID meldet Fehler als AADSTS-Codes. Details zu jedem Code: https://login.microsoftonline.com/error?code=[Nummer]

    AADSTS50126: Benutzername oder Passwort falsch

    Ursache: Der Benutzer hat falsche Anmeldedaten eingegeben

    Lösung: Ein gewisser Anteil ist normal. Ein plötzlicher Anstieg von wenigen IP-Adressen deutet auf Password Spraying hin: Sign-in Logs prüfen und MFA erwägen.

    AADSTS50053: Konto gesperrt oder Anmeldung blockiert

    Ursache: Zu viele Fehlversuche, oder die Anfrage kam von einer IP-Adresse mit schädlicher Aktivität

    Lösung: Fehlergrund in den Sign-in Logs prüfen. Benutzer informieren; die Sperre endet automatisch.

    AADSTS50011: Redirect URI stimmt nicht überein

    Ursache: Die von Power Pages gesendete Redirect URI passt nicht zur App-Registrierung

    Lösung: Beide Werte exakt angleichen (Schema, Host, Pfad, abschließender Schrägstrich). Typisch nach dem Umstieg auf eine eigene Domain.

    AADSTS700016: Anwendung nicht gefunden

    Ursache: Falsche Client ID, oder die Authority zeigt auf einen anderen Tenant

    Lösung: Client ID und Authority in Power Pages mit der App-Registrierung im externen Tenant vergleichen.

    AADSTS7000215: Ungültiges Client Secret

    Ursache: Nur mit Client Secret: Es ist abgelaufen, oder statt des Werts wurde die Secret ID eingetragen

    Lösung: Neues Client Secret anlegen und in Power Pages aktualisieren (siehe 4.3).

    6. Best Practices und Sicherheit

    6.1 Security Best Practices

    1. Prinzip der minimalen Rechte

    Vergeben Sie nur die minimal nötigen Berechtigungen für Dienst- und Admin-Konten. Nutzen Sie dedizierte Admin-Konten, keine persönlichen.

    2. Conditional-Access-Richtlinien

    Nutzen Sie Conditional Access im externen Tenant, um MFA zu verlangen oder den Zugriff zu blockieren. Externe Tenants bieten einen reduzierten Umfang: Bedingungen für Geräteplattform und Standort; Steuerungen Blockieren, MFA verlangen und Passwort-Reset verlangen. Risikobasierte Bedingungen (ID Protection) gibt es dort nicht.

    3. Umgang mit Client Secrets

    Falls Sie ein Client Secret verwenden: niemals in Code oder Konfigurationsdateien speichern. Nutzen Sie Azure Key Vault, rotieren Sie alle 6-12 Monate und dokumentieren Sie jeden Wechsel.

    4. Audit Logging

    Externe Tenants bewahren Sign-in- und Audit-Logs 7 Tage auf. Exportieren Sie sie per Azure Monitor nach Log Analytics, in ein Storage-Konto oder ein SIEM und bewahren Sie sie mindestens 90 Tage auf.

    5. Regelmäßige Security Reviews

    Führen Sie quartalsweise Security Reviews durch. Prüfen Sie: aktive Berechtigungen, MFA-Nutzungsquote, Muster bei Fehlanmeldungen, inaktive Konten.

    6.2 Performance und Betrieb

    Sitzung und Token-Laufzeit abstimmen

    Die Power-Pages-Einstellung "Use token lifetime" koppelt die Sitzung der Website an die Laufzeit des Tokens. Entscheiden Sie bewusst, ob Sie dieses Verhalten wollen.

    Claims minimieren

    Halten Sie Tokens klein: Fragen Sie nur die Benutzerattribute ab, die Sie tatsächlich brauchen.

    Eigene URL-Domain und WAF

    Lassen Sie die Anmeldung über Ihre eigene Domain laufen (z.B. login.contoso.com) und schalten Sie optional eine Web Application Firewall davor (Integration mit Azure Front Door, Cloudflare oder Akamai).

    6.3 Compliance und Datenschutz

    DSGVO-Konformität

    Wählen Sie beim Anlegen des externen Tenants ein EU-Land als Land/Region; das lässt sich später nicht ändern. Implementieren Sie Prozesse für DSGVO-Anfragen (Auskunft, Löschung, Berichtigung). Dokumentieren Sie alle Datenverarbeitungen.

    Datenstandort

    Der Datenstandort eines externen Tenants ergibt sich aus dem beim Anlegen gewählten Land/Region. Prüfen Sie ihn vor dem Anlegen gegen Ihre Compliance-Anforderungen.

    Einwilligungen verwalten

    Gestalten Sie klare Einwilligungen für die Datenerhebung. Dokumentieren Sie alle erhobenen Daten und ihren Zweck. Ermöglichen Sie einen einfachen Widerruf.

    7. Häufig gestellte Fragen (FAQ)

    Wie oft müssen Client Secrets rotiert werden?
    Nur wenn Sie ein Client Secret verwenden (siehe 4.3). Best Practice: alle 6-12 Monate; Microsoft empfiehlt maximal 12 Monate Gültigkeit. Dokumentieren Sie jeden Wechsel und stimmen Sie sich mit dem Power-Pages-Team ab.
    Können Benutzer ihre Konten selbst löschen?
    Nicht von Haus aus. Admins löschen Benutzer im Microsoft Entra Admin Center oder per Microsoft Graph. Custom Policies gibt es in External ID nicht; eine Selbstlöschung braucht daher einen eigenen Prozess (z.B. ein Anfrageformular). Löschen oder anonymisieren Sie auch den zugehörigen Kontakt in Dataverse.
    Was kostet Entra External ID?
    Abgerechnet wird nach monatlich aktiven Benutzern (MAU). Das Kernangebot ist für die ersten 50.000 MAU pro Monat kostenlos. Premium-Add-ons wie SMS für MFA haben kein Freikontingent. Aktuelle Preise stehen auf der offiziellen Preisseite von External ID.
    Wie lange werden Sign-in Logs aufbewahrt?
    In einem externen Tenant 7 Tage, für Sign-in- wie Audit-Logs. Für längere Aufbewahrung exportieren Sie sie per Azure Monitor nach Log Analytics, in ein Storage-Konto oder ein SIEM. Empfehlung: mindestens 90 Tage.
    Können Social Logins (Google, Facebook) verwendet werden?
    Ja. External ID unterstützt Google, Facebook, Apple und eigene OpenID-Connect-Provider. Richten Sie den Provider im externen Tenant ein und fügen Sie ihn dem User Flow hinzu. Beachten Sie die Datenschutzfolgen von Social Logins.
    Was passiert, wenn Entra External ID ausfällt?
    Registrierung und Anmeldung im Portal funktionieren nicht mehr; anonyme Seiten bleiben erreichbar. Ihre Verfügbarkeitszusagen dokumentiert Microsoft im Microsoft Online Services SLA. Prüfen Sie bei Ausfällen Azure Service Health und halten Sie einen Wartungshinweis für das Portal bereit.
    Wie viele parallele Sitzungen sind erlaubt?
    Ein Limit für gleichzeitige Sitzungen pro Benutzer ist nicht dokumentiert. Die Sitzungsdauer steuern die Power-Pages-Einstellungen (z.B. "Use token lifetime") und die Token-Laufzeiten in Entra. Access Tokens haben eine variable Standardlaufzeit von etwa 60 bis 90 Minuten.

    8. Checklisten

    8.1 Checkliste Ersteinrichtung

    Externer Tenant erstellt (EU-Land/Region)
    App-Registrierung konfiguriert (Redirect URI, ID Tokens, Admin Consent)
    User Flow für Registrierung/Anmeldung erstellt und getestet
    Passwort-Reset (Email OTP) aktiviert und getestet
    Company Branding konfiguriert (Logo, Farben)
    Conditional-Access-Richtlinie für MFA aktiv (mindestens für Admins)
    Integration mit Power Pages getestet (Registrierung, Anmeldung, Passwort-Reset)
    Log-Export per Azure Monitor eingerichtet (7 Tage Aufbewahrung im Tenant)
    Dokumentation erstellt (Konfiguration, Zugänge, Prozesse)
    Go-Live-Tests durchgeführt (alle Szenarien)

    8.2 Checkliste monatliche Wartung

    Sign-in Logs auf Auffälligkeiten geprüft
    Fehlgeschlagene Anmeldungen analysiert (< 5%)
    Inaktive Benutzer identifiziert (> 90 Tage)
    MAU und Kosten geprüft
    Ablaufdatum des Client Secrets geprüft, falls verwendet (< 30 Tage -> Rotation planen)
    Azure Service Health auf geplante Wartungen geprüft
    Konfiguration gesichert (App-Registrierungen, User Flows)

    8.3 Checkliste quartalsweises Security Review

    Admin-Berechtigungen geprüft (Prinzip der minimalen Rechte)
    MFA-Nutzungsquote geprüft (Ziel: > 90%)
    Audit Logs auf verdächtige Aktivitäten geprüft
    Anmeldemethoden und Passwort-Reset geprüft
    Einstellungen des User Flows geprüft (Attribute, Identity Provider)
    Conditional-Access-Richtlinien geprüft (MFA, Ausnahmen)
    Compliance-Dokumentation aktualisiert (DSGVO usw.)
    Notfallplan getestet

    Zusammenfassung

    Nach erfolgreicher Ersteinrichtung ist der administrative Aufwand für Entra External ID gering. Die meisten Wartungsaufgaben sind in wenigen Stunden pro Monat erledigt. Automatisierung (Alarme, Monitoring) senkt den manuellen Aufwand weiter.
